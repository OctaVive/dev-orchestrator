# P1-M08 — strict configuration normalization and agent policy

Implementation: guest-only `internal/configguest`, normalized-data
`internal/policy`, independent `internal/agentpolicy`, versioned
`internal/contracts` and `api/agent-v2.schema.json`.

See the [exact grammar and bounds](../../docs/project/specifications/configuration-policy.md),
[implementation plan](../../docs/project/PH1/P1M08/implementation-plan.md) and
[post-implementation test plan](../../docs/project/PH1/P1M08/test-plan.md).
Milestone status and actual acceptance evidence live in the
[milestone README](../../docs/project/PH1/P1M08/README.md).

The guest exports the immutable clone context, parses the explicitly selected
configuration under cgroup/time/output bounds and emits its bounded normalized
plan with clone success. Controller validation precedes atomic persistence of
source/context and plan in the private clone-attempt record. Audit/outbox records
contain identity and hashes, not environment values or argv. This avoids a second
configuration-control RPC while preserving durable source resolution and the
existing durable clone prerequisite for build authorization.

Build version 2 binds canonical plan hash. Storage and provisioner independently
check source/context, generation/attempt/lease, accepted plan and selected local
Dockerfile path. The guest reanalyses before invoking the unchanged pinned
rootless/offline BuildKit boundary. OCI parsing/scanning runs in a fresh separate
VM. Verified image metadata becomes part of the immutable admission result;
metadata values stay out of audit/outbox payloads.

Finalization accepts only current exact image admissions and app-owned
volume/secret handles supplied by trusted adapters. It applies numeric non-root
users, bounded resources, finite health/restart behavior, explicit ingress and
restricted-v1 controls. External image services require their own prior admission.
At most one locally built service is supported in this version; multi-build
scheduling is unsupported.

The runtime agent receives only strict spec v2, never YAML/Dockerfile/engine
options. Its own resolver and policy validation reject malformed, obsolete,
conflicting or dangerous normalized input even if controller checks were bypassed.
M09 must add signature/replay authorization, capability checks, actual engine
constraints and inspection. M10 owns storage/secret materialization; M12 owns
approval and full orchestration. Normalization/admission do not deploy or approve.
